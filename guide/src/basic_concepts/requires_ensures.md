# `requires` and `ensures`

Most of what you will be writing with creusot will be `requires` and `ensures` clauses, also called **preconditions** and **postconditions**.

Together, those form the **contract** of a function. This is in essence the "logical signature" of your function: when analyzing a function, only the contract of other functions is visible.

## Preconditions with `requires`

A _precondition_ is an assertion that must hold when entering the function. For example, the following function accesses a slice at index `0`:

```rust
fn head(v: &[i32]) -> i32 {
    v[0]
}
```

So we must require that the slice has at least one element:

```rust
#[requires(v@.len() >= 1)]
fn head(v: &[i32]) -> i32 {
    v[0]
}
```

Note the **view** (`@`) operator: it is needed to convert the Rust type `&[i32]` to a logical type `Seq<i32>`. Else, we could not call `[T]::len`, which is a program function (and not a logical one).

To learn more, see the chapter on [Pearlite](../pearlite.md) and [Views](../view.md).

## Postconditions with `ensures`

A _postcondition_ is an assertion that is proven true at the end of the function.
The return value of the function is named `result` by default.

In the case of the example above, we want to assert that the returned integer is the first of the slice:

```rust
#[requires(v@.len() >= 1)]
#[ensures(v@[0] == result)]
fn head(v: &[i32]) -> i32 {
    v[0]
}
```

Note that we:
- use the `@` operator on the slice to get a `Seq<i32>`
- we can then index this `Seq<i32>` to get a `i32`.

The result variable in an `ensures` clause can be bound explicitly using closure notation:

```rust
#[ensures(|resultat| v@[0] == resultat)]
```

The result binder can also be an irrefutable pattern.

```rust
#[ensures(|(fst, snd)| fst <= snd)]
pub fn apair() -> (i32, i32) {
    (0, 1)
}
```

## Contracts in traits

Contracts follow additional rules for methods in traits and their implementations. In short:

- The contract of a method implementation must **refine** the contract of its declaration.
- A method implementation without an explicit contract **inherits** the contract of its declaration, except if it is `#[requires(false)]`.

### Contract refinement

To enable generic reasoning about traits, trait implementations should
satisfy the specification given by the trait definition.

To achieve this, Creusot requires that the contract on a method implementation
**refines** the contract on the corresponding method declaration.

If a trait declares a method with precondition `PRE_DECL`
and postcondition `POST_DECL`, and an implementation of that method
has precondition `PRE_IMPL` and postcondition `POST_IMPL`,
Creusot generates a proof obligation of the following form,
in a file `${METHOD_NAME}__refines.coma`:

```
PRE_DECL ==> PRE_IMPL && (POST_IMPL ==> POST_DECL)
```

In particular, if the method declaration has the precondition `true`,
then its implementations must have the same precondition.

Another technique is to declare a method with precondition `false`
to let implementations set arbitrary preconditions.

### Contract inheritance

A common situation is for the contract of an implementation
to be the same as its declaration. To facilitate this use case,
a method without an explicit contract (no `requires`, `ensures`, or `variant`)
**inherits** the contract of the method's declaration.
No refinement obligation is generated by Creusot in this case
since it is trivially satisfied.

An exception to contract inheritance is when the method declaration has `false`
as its precondition (`#[requires(false)]`). This indicates that the contract is
entirely up to the implementation. Consequently, there is no contract inheritance,
and the method implementation just keeps its empty contract,
equivalent to `#[requires(true)]` and `#[ensures(true)]`.
